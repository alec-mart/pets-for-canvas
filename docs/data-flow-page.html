Where the Data Goes

Every field a time report carries, every hop it makes from a planner card to Postgres, every point where AI touches it — and which facts each layer can see. This is also the security story: the whole collection surface fits on one page.

01The report payload — what leaves the browser

One bucket tap produces exactly one report:

{
  "device_id":     "b3f2…",         // random UUID minted on install — resettable, anonymous
  "course_id":     1611537,          // from the planner row's link
  "assignment_id": 13824489,
  "kind":          "assignment",     // assignment | quiz | discussion
  "bucket":        "3_6",            // lt1 | 1_3 | 3_6 | 6_10 | gt10
  "title":         "Class Survey",
  "reported_at":   "2026-09-04T21:40:00Z"
}

Never in a payload: name, email, Canvas user id, grades, message content, browsing history. Clearing extension storage mints a new identity.

Today the payload stays in chrome.storage.local (popup shows and exports it). In Phase 1, storage becomes a write-through queue: POST /reports over HTTPS, retried until acknowledged, so offline taps never vanish.

02Identity and dedupe

  • Anonymous by default. A device_id, nothing else. Soft enrollment proof comes free: a report can only originate from the live planner page of a course the browser is actually logged into — trolling requires enrolling, unlike RateMyProfessors.
  • Never-ask-twice, enforced twice. Client-side asked-keys, plus UNIQUE(device_id, assignment_id) server-side.
  • Account-link is optional and later. Digest users connect Discord; their device joins to a user row, their reports gain weight in medians, and they unlock “you vs. class.” Unlinked reports stay first-class.

03The same-origin session API VERIFIED LIVE

The content script runs on mtu.instructure.com, so fetch('/api/v1/…') rides the user's logged-in session — no token, no OAuth, no onboarding. (Responses arrive prefixed with while(1); — strip it.) Tested Sept 2: courses?include[]=teachers returned every professor's name, 200 OK.

The extension's fetch list is fixed and documented (v2, amended 2026-09-03 for verified streaks/points):

① courses?include[]=teachers — once per term, cached. Course → professor/section map.
② courses/:id/assignments/:id — on report / estimate display.
③ users/self/missing_submissions — daily, for verified streaks.
④ own submission/grade state — on completion events; the economy pays only on receipts.

Everything on the list is the user's own data — never inbox, never discussion content, never anything about another user. The list grows only by documented amendment, never drift. It stays short enough to read aloud: the audiences are the store listing, security-minded reviewers, and Chrome's data-use review.

Capability vs. policy: session auth is close to full API power, writes included — the two-call budget is enforced by our shipped code and store review, not a technical wall. The defensible claim is “audit the list of calls our code makes,” never “we can't do more.” Digest tokens share this posture: full-power by nature, read-only by policy.

05Schema — Postgres, Phase 1

devices     (device_id PK, created_at, user_id NULL → users)
users       (id PK, discord_id, canvas_user_id, canvas_token_encrypted, created_at)   -- digest users only
courses     (canvas_course_id PK, campus, term, name, section_code, professor_name, updated_at)
assignments (canvas_assignment_id PK, canvas_course_id → courses, title, points,
             due_at, submission_types, description_hash, updated_at)
reports     (id PK, device_id → devices, canvas_assignment_id → assignments,
             bucket, reported_at, UNIQUE(device_id, canvas_assignment_id))
estimates   (canvas_assignment_id PK, source ENUM(llm, crowd), bucket_median,
             hours_hint, n, updated_at)

Descriptions are hashed for change detection, fetched on demand for the estimator, never warehoused. Token encryption at rest. Delete-my-data is a hard cascade from users and devices.

06Where AI touches the data — four points, only four

  1. The day-one estimator. LLM reads title, description, points, course context → a bucket, labeled “estimated.” Never dressed up as reported data. Long-run, accumulated (description → hours) pairs fit a model that transfers to new campuses — the terminal value of old reports.
  2. Assignment matching — three tiers, LLM last. Within a semester identity is free: reports key on assignment_id, which survives renames (only a description change matters — keep the reports, flag the estimate stale). Across semesters course copy mints new ids, so: exact (identical description hash — most of the volume, no AI), then fuzzy (title + points + due-week position), then LLM for the ambiguous middle, always with a confidence. A course's measured match rate becomes its stability score, so photocopy courses lean on history while volatile ones demote it to a weak prior. Display hierarchy, always labeled: reported this semester > reported last term, matched > estimated.
  3. Aggregation & quality. Bucket medians, never means. Minimum n = 5 before anything displays — the privacy floor, since small-n plus a professor label can deanonymize. Linked reports weigh more; extreme outliers trimmed.
  4. The digest prompt — the product's voice. Lives in the delivery layer and never touches raw reports.

Everything else in the pipeline is deterministic plumbing.

07Privacy invariants — the IT story, condensed

Anonymous reports, aggregate display. Nothing individual is ever shown; nothing displays below n = 5.
A one-breath collection surface. The extension reads pages the student already sees, plus two fixed metadata calls. Never grades, never inbox, never anyone else.
Tokens are guarded. Digest tokens encrypted at rest, used read-only by policy, and delete-my-data is a hard cascade.
Individual data is never sold. The only external product is aggregate workload analytics, behind the same n-floor.
